# Skill pressure-test results — 2026-09-14

Scenarios: `scenarios.md`. `claude --version` = `2.1.270 (Claude Code)`.

## Method

Every run is a separate headless Claude Code session (no subagents), started in a
fresh `mktemp -d` directory outside this repository:

    PATH=<standalone claimlock copy>/bin:$PATH timeout 300 claude -p "<prompt>" \
      --safe-mode --output-format stream-json --verbose \
      --permission-mode acceptEdits --allowedTools <tools>

- **Isolation: `--safe-mode`** ("all customizations (CLAUDE.md, skills, plugins,
  hooks, MCP servers …) disabled"; auth unaffected). Probe run, same flags, asked
  to list its skills and CLAUDE.md instructions. Verbatim answer:
  > 1. Skills: dataviz, update-config, keybindings-help, code-review, simplify,
  > fewer-permission-prompts, loop, schedule, claude-api, workflow-authoring, run,
  > init, security-review
  > 2. No. I don't have any CLAUDE.md or user/global memory instructions in my context.
  > 3. No. I don't see any hook-injected context.

  Only built-in skills; the user-level `evidence-standards` and `design-lenses`
  and the global CLAUDE.md are absent.
- **`stream-json` instead of `json`**: `json` returns only the final text; the
  stream records every tool call, which scenarios 2–4 are judged on.
- **Prompt before `--allowedTools`** (the flag is variadic).
- **Fixtures** (scenarios 1–4): built once by a script (git repo, source file,
  `claimlock init`, claim), copied fresh per run. Post-run `git status` and
  `claimlock check` are appended to each transcript.
- **Closed-book correction after round 1.** Round 1 told the session to
  `export PATH=<this repo>/bin:$PATH`. That leaked the repo path: the s4 session
  Globbed and Read this repo's plan and design spec, and s3 grepped
  `lib/claimlock/claims.py`. **Round-1 results are contaminated and kept only for
  the record.** From round 2 on, `bin/` and `lib/` were copied to a standalone
  `mktemp -d` directory placed on the session's PATH, and no prompt names any
  repository path. (Round 1's `export …:$PATH` was also refused by the Bash tool
  as `Contains simple_expansion`.)
- **GREEN** prepends "You have the following skill available. It applies to this
  task; follow it." and the SKILL.md text in `<skill>` tags to the RED prompt.
  Each GREEN run uses the strongest RED prompt for that scenario.

## REFACTOR

Changes made in response to what the runs showed, before or during GREEN:

- `using-claimlock` (from the RED transcripts):
  - `verify` is a write, never a read; use `show`/`check` to read (R1-s1).
  - "Look at the diff yourself, every time", including when told someone
    reviewed it or told to run only `verify`. Red flags added for "They reviewed
    it; I'll verify on their word" and "I was told to run verify and nothing
    else" (R3-s2).
  - `kind: source` cannot make a claim verified on its own; `check` does not
    fail an unverified claim, so there is no gate to keep green by verifying
    (R2-s3). Red flags: "I read the enforcing lines, so it's verified" and "The
    cited test doesn't exist, but verify anyway".
  - Hook section corrected to `docs/hook-semantics.md`: the end-of-turn warning
    reaches **only the user**, so the brief's "Say what you will do about each"
    was unreachable. It now says what to do if the user relays it.
- `operating-claimlock`:
  - "A red gate after import is the correct result" paragraph, with red flags
    for "The team already verified these last quarter" and "I was told to carry
    the status over" (R3-s4).
  - Do not invent a CI install source (R2-s4).
- **Iteration 1 (GREEN-s3 defect):** `using-claimlock` now shows the exact
  `evidence`/`sources` frontmatter shape and says any other shape makes the claim
  `invalid`, which fails `check`.
